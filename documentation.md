# Operation Prodi - Feature Guide

## 1. How to Use This Document

Purpose:
- This is an implementation guide for engineers and AI agents working on unfamiliar features.
- Use it to find the relevant route, components, hooks, data flow, and persistence model before editing.
- Start with `docs/README.md` when deciding which documentation file is relevant.

Precedence:
- Code and migrations are the source of truth.
- Use this guide as a map, not as permission to assume behavior without checking the implementation.
- `docs/database-guide.md` is authoritative for nutrition-data and Supabase schema details.

Working assumptions:
- Production UI lives under `app/(app)`.
- Auth routes live under `app/(auth)`.
- `app/page.tsx` redirects to `/dashboard`.
- Most stateful features use Supabase-first persistence with `localStorage` fallback where noted.
- `middleware.ts` enforces auth/RBAC whenever Supabase is configured. `NEXT_PUBLIC_DISABLE_AUTH_FOR_TESTING=true` is the temporary local-only bypass.

Validation note:
- Prefer proportional validation. Use the lightest reliable check for the area you changed.
- For nutrient math changes, run `npm run validate:nutrients`.
- For workflow changes, run the most relevant Playwright coverage instead of defaulting to the full suite.

Agent quick index:
- Food/search/reference data: sections 4.2, 4.6.1, 4.12, 6 and `docs/database-guide.md`.
- Recipes/plans/exports: sections 4.3-4.5, 4.7, 4.9, and 4.17.
- Patient workspace/client diary/counseling: sections 4.6, 4.8, 4.16, 4.24, and 4.26.
- Institution/hospital workflows: sections 4.19-4.23.
- Auth/RBAC/admin/export surfaces: sections 4.9-4.11 and 4.15 plus `AGENTS.md`.

## 2. Global Architecture Overview
- **Rendering:** Next.js 16 with server rendering and `<Suspense>` boundaries for heavier routes.
- **Caching:** BLS food data is cached via `unstable_cache` where applicable.
- **Layout stack:** `app/layout.tsx` applies fonts, theme provider, toasts. `app/(app)/layout.tsx` wires the `SidebarProvider`, `AppSidebar`, the header breadcrumb, and contextual food search. Food search is shown only on food-heavy routes and remains **non-blocking** because the search index is lazy-loaded on demand.
- **Responsive contract:** Shared layout primitives (`PageHeader`, `SidebarInset`, `Card`, `TabsList`, `Table`, and the contextual food search trigger) should keep document-level width within the viewport. Wide tables scroll inside their own container rather than widening the page. `tests/responsive-layout.spec.ts` checks 390 px, 768 px, and desktop widths across dashboard, foods, patients, reports, institution, and API/export routes.
- **Clinical status tokens:** `lib/clinical-status.ts` defines reusable tone classes for source trust, review, risk, and success states. Use these instead of one-off color choices when a badge communicates clinical meaning.
- **Contextual food search:** `components/food-search-command.tsx` provides the `cmd+k` food search trigger on food-heavy routes. The search index is loaded on first use via `/api/foods/search-index`.
- **Mock data + utilities:**
  - `@/lib/nutrients.ts`, `@/lib/reference-values.ts`, and `@/lib/sustainability.ts` implement calculation logic shared across features.
- **Stateful hooks:** CRUD hooks in `hooks/` (e.g., `usePatients`, `useCustomFoods`, `useRecipes`) follow a **Supabase-first with local fallback** pattern where implemented. Data is synced to the cloud when authenticated but remains available in `localStorage` for offline use.
- **Reference values:** Official DGE/ÖGE/SGE/RDA rows now load from Supabase. Custom profiles, user defaults, and patient-specific assignments persist remotely with bundled fallback data for pre-migration environments.
- **Export pipeline:** Real file generation lives behind authenticated server routes in `app/api/exports/*`. Client pages build typed payloads, the server renders PDF/CSV output, and export metadata is written to `export_jobs`.

## 3. Data & State Layers
- **Supabase-First Persistence:** 
  - **Patients, Recipes, Meal Plans, Institution Menu Plans, Client Diary, Invoices, Appointments:** All have backend persistence.
  - **Counseling workflow:** Counseling sessions and counseling templates now persist in Supabase with local fallback and login-time migration from older local-only browser data.
  - **Patient clinical workspace:** Anthropometrics, diagnoses, medications, screenings, lab values, and activities are persisted in Supabase with automatic local fallback and login-time migration where documented.
  - **Still local-only in the patient workspace:** Demo analytics panels and assistant cards remain client-side only unless otherwise noted.
  - **Auto-Migration:** Hooks migrate dirty local data to Supabase on login where that behavior is implemented.
  - **Robustness:** All database calls use `withTimeout` and `try-catch` to ensure the UI stays responsive even if the backend is slow.
- **Foods & Search:**
  - **Search-on-Demand:** Instead of pre-fetching the full food catalog, the app uses a lightweight search index. Full food details are fetched only when needed.
  - **Server-backed foods browser:** `/lebensmittel` no longer hydrates the full list view into the client. The route loads an initial paginated server result and the client fetches subsequent pages through `/api/foods/browser`.
  - **Client-safe fetchers:** `lib/data/foods-client.ts` provides optimized browser-side Supabase queries.
- **Scientific Integrity:** 
  - All nutrient calculations are mathematically validated against the BLS 4.0 ground truth via `scripts/validate-nutrient-math.ts`.
- **Cached Recipe Nutrients:** Recipes store their calculated totals in the database (`cached_kcal_per_portion`, etc.) to allow for instant rendering in lists without ingredient hydration.
- **Logging convention:** Use `createLogger(scope)` from `lib/log.ts` instead of raw `console.*` — server output is one JSON line per entry (filterable by level/scope), error details go into `meta`. `lib/data/foods.ts` and `lib/data/practice-overview.ts` are migrated; remaining `console.*` call sites migrate opportunistically when files are touched.
- **localStorage fallback layer:** `lib/data/local-*.ts` persists meal plans, recipes, and selected clinical records in browser `localStorage` as an offline/auth-optional fallback and as the source for login-time migration (`lib/data/local-records.ts` matches local vs. remote identity). **Privacy note:** this stores unencrypted health-related data in the browser profile; on a shared clinic PC any OS user of the same browser profile can read it, and it is not wiped on logout. Open decision (follow-up): keep write-path only for auth-optional mode, switch to session-only storage, or remove the fallback entirely once Supabase auth is mandatory.

## 4. Feature Reference
Each subsection includes route, core components, important hooks/utilities, and extension notes.

### 4.1 Dashboard (`/dashboard`)
- **Weekly work surface:** `app/(app)/dashboard/page.tsx` fetches the user's patients, plans, appointments, counseling sessions, and intake submissions in parallel. `dashboard-overview-client.tsx` renders Monday through Sunday as a selectable calendar, with previous week, next week, and today controls. Saturday and Sunday remain visible but muted. The appointments for the selected day sit directly below it.
- **Prioritized work list:** `lib/dashboard-worklist.ts` derives actions from existing records only. Returned intake questionnaires lead, followed by open plans and active patients whose last documented contact is at least 42 days old and who have no future appointment. It never writes reminders or clinical state.
- **Overview cards:** open questionnaires, active patients, open plans, and appointments in the selected calendar week sit above the calendar. Recent patient files and meal plans stay below the weekly work surface. The former separate appointment block and the `Großen Kalender öffnen` link were removed.
- **Empty workspaces:** every area keeps a useful empty state and a direct action instead of showing invented demo appointments.

### 4.2 Lebensmittel (Foods) (`/lebensmittel`)
- **Listing + search:** `app/(app)/lebensmittel/page.tsx`
  - Server page calls `fetchFoodsBrowserPage()` for the initial result set and the initial OFF-branded tab payload.
  - Client page (`lebensmittel-client.tsx`) keeps the existing search modes and filters, but fetches page changes through `/api/foods/browser`.
  - Hooks: `useCustomFoods`, `useFoodSynonyms`, `useFoodSourcePreference`.
  - UI: Search mode buttons, filters (source, categories), paginated desktop results table, mobile result cards, OFF-branded products tab.
  - **Active database (PRODI-feedback #3):** the source selector is the persisted "Aktive Datenbank" choice, not a throwaway filter. `useFoodSourcePreference` (`hooks/use-food-source-preference.ts`) stores the selected `FoodSourceId | "all"` in `localStorage` (module-store + `useSyncExternalStore`, default `"all"`) so it sticks across visits; a "Gespeichert"/"Alle Quellen" badge sits next to the selector. Each food row still shows its own source as a trust-tone badge (`getFoodSourceTrustTone`).
  - **Nutrient sort & filter (PRODI-feedback #4):** a collapsible "Nach Nährstoff sortieren & filtern" panel lets the user pick one nutrient from `NUTRIENT_DEFINITIONS` (grouped by makro/vitamine/mineralstoffe/fettsäuren/aminosäuren/sonstige), order **höchste/niedrigste zuerst**, and set optional **Min./Max.** thresholds (per 100 g). When active, the chosen nutrient is added as a dedicated result column (desktop table + mobile card) and shown in the result-count line. Runs server-side across the whole catalog via the `filter_foods_by_nutrient` RPC, composing with the source/category/group filters; local custom foods are threshold-filtered and re-sorted client-side via `filterLocalCustomFoods`. Query params: `nutrientId`, `nutrientSort` (`asc`/`desc`), `nutrientMin`, `nutrientMax` on `/api/foods/browser`.
  - Mobile food cards prioritize identification and nutrient scanning: name, source/category badges, kcal, Eiweiß, Fett, and KH. Alias management is available as a secondary expandable action so lookup cards stay compact.
  - Data: `FOOD_CATEGORIES`, `FOOD_SOURCES`, `FOOD_GROUPS`, `NUTRIENT_DEFINITIONS`, `fetchFoodsBrowserPage()`, `/api/foods/browser`.
- **Group navigation:** `FoodGroupTree` uses `FOOD_GROUPS`; ensure new groups update `getFoodGroupDescendants`.
- **Curated-first browse order:** with no search query the catalog is ordered `is_branded ASC, name ASC`, so the ~7k curated BLS/SFK reference foods lead and the ~94k branded Open Food Facts products follow. This mirrors the ranking the name-search RPCs already apply (`20260629000066_search_bls_priority`); before it, plain name order opened `/lebensmittel` on OFF products whose names start with punctuation ("_Muffins von Kathi") and buried the clinical catalog. Backed by `idx_foods_is_branded_name` (`20260812000086`) — without that index the two-key sort over ~101k rows plus the `food_nutrients` embed exceeds the Postgres statement timeout and the list renders empty, the same failure `20260629000068` fixed for the plain name browse.
- **Search contract:** name-mode search prefers the `search_foods_with_total` RPC, falls back to `search_foods()` if the new migration has not been applied yet, and finally falls back to a direct paginated Supabase name query if both RPCs are unavailable or out of sync. Code/group/browse modes use direct paginated Supabase queries. When a nutrient sort/threshold is active, browsing instead routes through the `filter_foods_by_nutrient` RPC (`fetchFoodsBrowserPageByNutrient`), which falls back to the direct query path if the RPC is unavailable.
- **Custom foods:** Page 1 still merges local custom-food migration candidates so offline or unauthenticated entries remain visible, but authenticated saves now canonicalize to Supabase IDs immediately and localStorage keeps only unmigrated/offline entries.
- **Synonyms:** `useFoodSynonyms()` now reads seeded system aliases from Supabase `food_synonyms` via `lib/data/food-synonyms-client.ts` and merges them with local user-created aliases stored in `localStorage`. The foods UI no longer bootstraps synonym seeds from `lib/mock-data`.
- **Source coverage transparency (PRODI-feedback #3):** the food detail nutrient tables distinguish a nutrient the source does **not measure** (no entry in `food.nutrients`, rendered as italic `n. e.` with a legend) from a measured `0`, since coverage differs per database. Implemented in `components/food-detail-content.tsx` (`NutrientTabContent`). The same distinction holds at group level: **every** nutrient group keeps its tab even when the source measured nothing in it, and the tab body says so ("Keine Daten für dieses Lebensmittel …"). Tabs used to be dropped when empty, which made a sparse OFF product indistinguishable from a food the app has no vitamin view for.
- **OFF details:** Foods with `sourceId === "off"` show attribution ("Produktdaten von Open Food Facts") and `dataQualityScore` in the detail page.
- **SFK foods:** Foods with `sourceId === "sfk"` come from the Souci-Fachmann-Kraut database (second primary data source alongside BLS). SFK foods expose expanded nutrient groups — `aminosaeuren` (18 amino acids) and `fettsaeuren` (13 detailed fatty acids) — in the food detail page nutrient breakdown when those values are present. SFK access is gated by `NEXT_PUBLIC_SFK_ENABLED`; when disabled, `canAccessDataSource("sfk")` returns false, SFK foods are filtered from search results and the food search index, and the food detail page shows a `Lizenzhinweis` banner. Entitlement logic lives in `lib/data/entitlements.ts`.
- **New custom food:** `/lebensmittel/neu` does not hydrate the catalog. It uses `useCustomFoods([])` only for the create/persist flow because submission does not need base foods.
- **Food comparison:** `/lebensmittel/vergleichen` uses search-based `ComparisonFoodPicker` components that query `/api/foods/browser` on demand instead of loading the full catalog. The picker searches both name/RPC results and BLS/source-code matches, then merges branded foods from `fetchBrandedFoods()` client-side for local matches.
- **Exchange tables:** `/austauschtabellen` is a standalone replacement-finding workflow. Users can pick an original food through `/api/foods/browser`, set the original amount, choose a lead nutrient, filter candidates by category/search, and rank candidates by similarity or nutrient amount. The table shows equivalent grams for matching the lead nutrient, deltas at the original amount, macro/fiber delta chips, top-match cards, and copyable counseling text. The client still avoids hydrating a server-side `Food[]` catalog: blank/category browsing uses the shared food search index from `useFoodSearch()`, candidate values come from `useNutrientValueMaps()`, and typed candidate search uses `/api/foods/browser`.

### 4.3 Rezepte Overview (`/rezepte`)
- **Component:** `app/(app)/rezepte/page.tsx`
  - Uses `<Suspense>` for the recipe list.
  - **Cached Rendering:** Recipe cards display kcal/macros instantly using cached values from the `recipes` table, avoiding heavy ingredient loading for the entire list.
  - **Meal-Master Import:** Supports uploading legacy `.mmf` or `.txt` recipe formats. Parses the file structure and uses NLP to intelligently match string ingredients against the BLS database. If an ingredient cannot be perfectly matched, an interactive `RecipeImportReviewDialog` is presented allowing the user to manually search and resolve the ingredient before saving.

### 4.4 Recipe Detail (`/rezepte/[id]`)
- **Routing:** `app/(app)/rezepte/[id]/page.tsx` fetches the recipe from Supabase.
- **Optimization:** No longer loads the full ~101,000-item catalog.
- **Hydration:** The page fetches recipe metadata first, then **asynchronously hydrates** only the specific foods used as ingredients via `fetchFoodsByIds`.
- **Dynamic CO₂ footprint:** Computes per-ingredient and per-portion CO₂ from `computeIngredientCo2()`. Ingredients table includes a CO₂ column. Sustainability card shows total, per-portion, plant/animal share bar, and top emitters.
- **LMIV allergen declaration:** Auto-derives allergens from ingredient foods using three strategies (explicit `food.allergens`, BLS food-group inference, name-token matching via `ALLERGEN_DEFINITIONS`). Merges with manually declared allergens and renders LMIV-compliant badges with auto-detection indicators. Core logic in `lib/allergen-derivation.ts`.

### 4.5 Recipe Form (`/rezepte/neu`, `/rezepte/[id]/bearbeiten`)
- **Component:** `components/recipe-form.tsx`
  - Uses `FoodSearchDialog` for on-demand ingredient selection.
  - **Local-Save First:** Always persists to `localStorage` before attempting Supabase sync, ensuring data safety for offline/unauthenticated users.
  - **Nutrient Caching:** Automatically calculates and persists calorie/macro totals into the `recipes` table for performant list rendering.
  - **Auto-computed on save:** CO₂ per portion is computed from live ingredients and stored alongside the recipe. Allergen checkboxes highlight auto-detected allergens from ingredients; on save, derived and manual allergens are merged.

### 4.6 Patient Detail (`/patienten/[id]` + nested tabs)
- **Clinical record core:**
  - Anthropometrie, Diagnosen, Medikamente, Screening history, Laborwerte, and Aktivität use Supabase-first persistence with offline `localStorage` fallback where documented.
  - The patient-detail tabs show sync-aware empty states while remote data is loading after authentication.
  - The patient detail header exposes a confirmed `Löschen` action. `usePatients.deletePatient()` removes the local row optimistically, deletes the Supabase patient record when authenticated, and restores the local row if the remote delete fails.
  - The patient workspace exposes a patient-bound `ReferenceProfileSelector`, so nutrient comparisons use the same persisted reference assignment for that patient.
  - Reference standard/life-stage and energy needs are consolidated into one **Referenzwerte & Energiebedarf** card in the `Aktivität & Energie` tab: the `ReferenceProfileSelector` sits above a Grundumsatz × PAL = Tagesbedarf breakdown (Mifflin-St Jeor BMR). The PAL factor persists per patient on `patient_reference_assignments.pal_value` (added in `20260604000053_patient_reference_pal.sql`) via `useReferenceProfiles().setPal`, defaulting to `1.4` when unset; a "Gespeichert"/"Standardwert" badge reflects persistence state. The same factor is editable on the patient overview's energy card, and `derivePalFromActivity` (`lib/intake/apply-submission.ts`) seeds it from the intake's own answers — job activity plus training days — when a submission is applied and no PAL is set yet. The ladder itself lives once in `PAL_LEVELS` (`lib/nutrition/energy-calculation.ts`).
- **Client diary:** The former practitioner-owned nutrition-protocol UI was removed. Ongoing self-documentation now happens in the consent-based client mode; see section 4.26. Existing database migrations are historical schema records and are not a description of an active protocol surface.

### 4.6.1 Referenzwerte (`/referenzwerte`)
- **Component:** `app/(app)/referenzwerte/page.tsx`
  - **Vergleich** tab compares the enabled standards (DGE, ÖGE, SGE, RDA — gated by `ENABLED_REFERENCE_STANDARDS` in `lib/reference-metadata.ts`) side by side for a chosen age group/gender, grouped by nutrient group with a per-row spread badge. Saved custom profiles can also be toggled in as comparison columns (via `resolveCustomProfile`); since they carry a fixed demographic, their column header shows the profile's age group/gender as a sublabel rather than following the age/gender selectors.
  - **Eigene Profile** tab creates `CustomReferenceProfile`s on top of a base standard/demographic. Per-nutrient overrides are edited through `NutrientOverrideTable`: each nutrient row has a **Schieberegler** that scales the value relative to its base (`SCALE_MIN`–`SCALE_MAX` % of standard, 100 % = base) with a live `%` readout, plus a direct **Zielwert** input for exact/out-of-range entry. Overrides equal to the base are dropped, derived nutrients (`energie_kj`, `broteinheiten`) are not adjustable, and nutrients without a base value fall back to direct entry. Profiles persist via `useReferenceProfiles().saveCustomProfile` → `reference_profiles`/`reference_profile_values` (no schema change for scaling — overrides remain absolute amounts). The read-only profile summary tags each override with its `%` delta versus base.

### 4.6.2 Kalorienrechner (`/kalorienrechner`)
- **Component:** `app/(app)/kalorienrechner/page.tsx` (client). Sidebar entry in the **Ernährung** section.
  - The shared `lib/nutrition/energy-calculation.ts` calculates Grundumsatz (Mifflin-St Jeor or Harris-Benedict), Gesamtbedarf (BMR × PAL), daily target (±1000 kcal balance with a 7700 kcal/kg weekly prognosis), BMI, and macro grams. The same Mifflin result is shown in the patient record.
  - The radial gauge uses a dynamic scale. Very high values remain readable and are never silently cut off at 4.000 kcal.
  - **Patient-aware:** an optional patient selector (top-right) and the `?patientId=` deep link load the patient's values — gender, age (from `dateOfBirth`), latest weight/height from `patient_anthropometrics`, PAL (mapped from `patient_reference_assignments.pal_value`), and saved `macroPreset`/`goalWeight`/`dailyCalorieGoal`. Applied once per selection after weigh-ins finish syncing.
  - **Im Patienten speichern:** waits for `dailyCalorieGoal`, `goalWeight`, `macroPreset`, PAL, and a changed weigh-in to be written before it reports success. Maintenance calories are derived live (BMR × PAL), not stored.
  - **Schema:** `patients.daily_calorie_goal`, `patients.goal_weight`, `patients.macro_preset` (migration `20260619000058_patient_calorie_targets.sql`), `patients.basal_metabolic_rate_override` (`20260818000090`), `patients.plan_principles` (`20260818000092`).

### 4.7 Berichte (removed)
- The standalone `/berichte` route and the per-patient report history (`PatientBerichteTab`, `patient_reports`/`patient_report_versions`, the `patient-report-files` storage bucket, report text templates, and the `/api/patient-report-versions/[versionId]/download` route) were removed. Per-patient analytics now live in the **Verlauf und Statistik** section of the patient overview (`components/patient-stats-tab.tsx` with `embedded`); migration `20260619000059_drop_patient_reports.sql` drops the tables.
- The shared `/api/exports/report` endpoint is retained: it still generates plan PDF/CSV files for the Ernährungsplan editor and dataset exports, but no longer persists patient-bound report records. Rendering lives in `lib/exports/pdf.tsx` and CSV formatting in `lib/exports/csv.ts`.

### 4.8 Patient Screens (`/patienten/aufnahmen`, `/patienten`) and Mail Merge (`/api-export`)
- **One patient journey (`lib/patient-journey.ts`):** the chain is einladen → prüfen → beraten → planen → betreuen. `/patienten/aufnahmen` is the work queue for invitations and first-plan preparation. `/patienten` shows every existing patient record immediately; a record without a patient-bound plan is marked `Erstkontakt offen`.
- **Four intake stages:** `eingeladen` → `fragebogen` → `beratung` → `plan`, derived from intake links, submissions, plan summaries, appointments and counseling sessions. A reviewed intake goes directly to `plan`; a consultation is optional and only holds the person in `beratung` when one is scheduled or manually selected. `buildIntakeRows()` returns the rows and `countByStage()` feeds group heads and board columns. The patient list uses `CareUrgency`, including `erstkontakt` for a record without a plan.
- **Derived, with one documented exception:** there is no stored stage column. The exception is `patients.intake_stage_override` (migration `20260812000085`), a nullable hand-set stage for a practitioner who knows something the records do not show yet. An overridden row carries `stagePinned` plus its `derivedStage`, the board marks it with a pin icon, and the card menu offers a one-click return to the derived stage. Both patient readers tolerate the columns being absent, so the code is safe to deploy before the migration is applied.
- **Views:** Liste (grouped by stage), Zeitachse, and Board. View, filters, grouping and sorting all live in the URL via `hooks/use-list-url-state.ts`, so a filtered list survives a reload and can be pasted to a colleague. When the plain Aufnahmen route is opened from navigation, it restores the practitioner’s last selected view from the browser; an explicit URL view still wins.
- **Independent navigation:** Aufnahmen is a top-level work page, so its breadcrumb contains only `Aufnahmen`. The green primary action creates an invitation; manual patient creation remains available as a secondary action.
- **Board (`components/intake-board-view.tsx`):** four columns that each ask for 268px, refuse to shrink and are free to grow — one rule instead of breakpoints, so the track scrolls sideways on a narrow screen rather than collapsing into stacked lists. The document itself never scrolls horizontally.
- **Dragging states an intent, not a fact (`lib/intake-transitions.ts`):** because a stage is derived, a drag cannot simply set it. `resolveIntakeTransition()` answers which single fact is missing and what supplies it; the dialog offers exactly that action (apply the waiting questionnaire, create the record, document the session) and the card then moves on its own. Where only the invited person can act — nobody in the practice can answer someone else's questionnaire — the dialog says so. Every move is also on a per-card menu, since drag-and-drop is unusable with a keyboard and unreliable on a tablet.
- **Review and handoff:** a returned submission opens `PatientIntakeReviewEditor`. The practitioner can correct identity, goal/body, health, diet, allergens and food ratings; add an internal review note; or discard the submission after confirmation. `lib/intake/review-rules.ts` flags deterministic contradictions such as vegan plus dairy, halal plus pork, or crustacean intolerance plus prawns. These are clarification prompts, never medical decisions. Applying persists the corrected payload and review note, adds the note to the patient file, then offers `Patientenakte öffnen` as the primary action, `Ernährungsplan erstellen`, or `Später`; no appointment is created or invented. Existing patient identity data remains authoritative instead of being overwritten by a questionnaire.
- **Plan summaries:** `fetchPatientPlanSummaries` in `lib/data/meal-plans.ts` selects only `patient_id,status,date`, so the list never joins `meal_entries` just to learn that a plan exists.
- **Mail merge moved:** serial mailings and the birthday list live in `components/patient-mailings-panel.tsx`, mounted on the `Serienbriefe` tab of `/api-export`. They are batch document generation, not a patient view.
- **Components:** `app/(app)/patienten/aufnahmen/page.tsx` (intake) and `app/(app)/patienten/page.tsx` (ongoing care)
  - **Patient creation intake:** `components/patient-form.tsx` now separates identity/status, contact/consent, address/contact person, and clinical intake context. New patient records can store care setting, external patient number, case number, preferred contact/language, communication and digital-protocol consent, referrer/department, intake reason, patient goals, clinical notes, admin notes, and emergency contact metadata.
  - **Duplicate guard:** The patient form warns before saving when another patient matches insurance number, external patient number, or name plus date of birth.
  - **Post-create handoff:** New patient creation can continue directly to the patient workspace, first counseling session, or back to the patient list.
  - **Patient rows:** the list derives `Letzte Beratung` from real `useCounseling()` session data instead of the legacy `COUNSELING_SESSIONS` mock constant, and shows it alongside the derived stage.
  - The authoring UI for templates/placeholders is still client-side and reads bundled product defaults from `lib/patient-mailings.ts`.
  - **Real exports:** `Dokumente erzeugen` now renders a merged PDF via `/api/exports/mail-merge` instead of creating a local text bundle.
  - **Batch tracking:** the existing client batch history is still used for UI state, but the actual export is also logged to `export_jobs`.

### 4.9 API & Export (`/api-export`)
- **Component:** `app/(app)/api-export/page.tsx`
  - Export cards now call `/api/exports/datasets` with typed `format` + `scope` combinations.
  - The default report export builder resolves references via the same user preference pipeline used in the interactive UI.
  - **Supported v1 scopes:** CSV for Lebensmittel/Rezepte/Patienten/Ernährungspläne/Berichte, JSON for Lebensmittel/Rezepte/Patienten/Ernährungspläne, PDF for Patienten/Berichte.
  - **History:** the `Verlauf` tab loads real persisted rows from `/api/export-jobs`; the former mock `EXPORT_HISTORY` list is no longer the source of truth for exports.
  - Failed history loads are shown inline so the export page does not silently degrade when the journal endpoint or schema is unavailable.
  - Export-journal failures include explicit recovery hints for missing `export_jobs` migrations or unavailable `/api/export-jobs` responses.
  - **API keys:** Owner/admin users can issue, list, and revoke live API keys from the REST API tab. Tokens are stored only as SHA-256 hashes in `api_keys`, the full token is shown once, and create/revoke events are written to `access_audit_logs`.
  - **External API boundary:** `POST /api/exports/datasets` accepts `Authorization: Bearer prodi_...` for the `exports:datasets:read` scope. Patient, meal-plan, recipe, and report API scopes still require cookie-authenticated app sessions until their integration contracts are hardened.
  - **Truth model:** Export creation, export history, and API-key issuance are live. FHIR/DEBInet/BI connector activation remains future integration work.
  - **Import status:** The import card is now explicitly labeled as planned instead of simulating a live upload workflow.

### 4.11 Admin & Sicherheit (`/admin/users`)
- **Component:** `app/(app)/admin/users/page.tsx`
  - The route is backed by persisted Supabase RBAC membership records and requires an `owner` or `admin` membership.
  - Team membership, invitations, role/status changes, report retention, and SSO configuration are backed by Supabase.

### 4.25 Patient Onboarding via Invite Link (`/onboarding/[linkId]`)
- **Purpose:** Let a practitioner collect goals, constraints, diet style, food preferences, and daily habits from a person before that person exists as a patient record. Advances `docs/user-priority-feedback.md` must-have #1 (low onboarding effort).
- **Public surface:** `app/onboarding/[linkId]/page.tsx` (server guard) + `patient-intake-form.tsx` (client wizard) under a minimal, mobile-first layout. Unauthenticated; `/onboarding` is in `PUBLIC_PREFIXES` in `lib/supabase/middleware.ts`.
- **Guard screens:** invalid UUID, unknown link, already submitted, expired, and non-active status each render their own message instead of the form.
- **Wizard:** 11 steps (Person, Ziel, Körper, Bewegung, Gesundheit, Unverträglichkeiten, Ernährungsform, Lebensmittel, Alltag, Erfahrung, Einwilligung). Only Person, Ziel, Körper and the consent checkbox are required. Progress is persisted to `localStorage` under `inari_intake_draft_${linkId}` on each step transition and cleared on success.
- **Food preference grid:** three-state (`gerne` / `geht` / `nie`) over the ~40-item catalog in `lib/intake-food-preferences.ts`, grouped by food group. This produces the per-patient whitelist that later drives swap suggestions.
- **Invitations are not bound to a patient:** `patient_intake_links.patient_id` is nullable. A `NULL` value means the patient record is created on apply; a set value means an existing patient is being re-onboarded.
- **APIs:**
  - `POST /api/onboarding/submit` — public, service-role, zod-validated, 200 KB size guard. Verifies link state, auto-expires past `expires_at` (410), rejects non-pending links (409), inserts one submission (unique per link), flips the link to `received`, and writes an audit log that never contains payload contents.
  - `POST /api/patient-intake-submissions/apply` — authenticated. Accepts an optional corrected payload and review note, re-validates them, then creates or updates the patient, upserts `patient_allergens` and `patient_food_preferences`, records one `patient_anthropometrics` entry, and marks the submission `applied`. Applying twice returns 409.
  - `POST /api/patient-intake-submissions/review` — authenticated. Marks a reviewed response `discarded` without deleting the original response and writes an access audit event.
- **Apply semantics:** patient-reported values never overwrite a non-empty practitioner field (`mergePatientUpdate` in `lib/intake/apply-submission.ts`); reviewed identity fields always win. A review note is appended to `patients.admin_notes`. Self-reported allergens are stored with a default severity and an explicit "nicht bestätigt" note.
- **Practitioner surfaces:** invitations appear directly in the `/patienten` list as `Eingeladen` / `Antwort da` rows with inline copy-link and review actions (see 4.8); `components/patient-intake-panel.tsx` (list, copy link, revoke, review, apply) remains mounted inside the patient `Ernährung` tab for re-onboarding. `components/patient-intake-invite-dialog.tsx` creates an invitation and renders the link plus a QR code generated in the browser via `qrcode` — QR payloads are never persisted.
- **Diet style vs exclusions:** `patients.diet_style` holds exactly one `DietStyle`; `patients.nutrition_preferences` holds many `DietExclusion` values. Vocabulary and the legacy-value reader live in `lib/diet-constants.ts`.
- **Plan principles (not wired up):** `lib/nutrition/principles.ts` derives up to five patient-readable rules from the calorie goal, macro preset (`lib/nutrition/macro-presets.ts`), diet line targets, and DGE fiber reference, rendered by `components/plan-principles-card.tsx`. It was written against the pre-rebuild planner, which computed day totals in the page client; the current `/ernaehrungsplan` delegates that to `usePlanAnalysis` and `PlanDayWorkspace`, and already surfaces diet-line and micronutrient compliance. The card is therefore **not rendered anywhere** — decide whether it earns a place next to the existing analysis rail before wiring it in. `lib/nutrition/macro-presets.ts` itself is live, used by `/kalorienrechner`.

### 4.26 Klientenmodus (`/klient`)
Second product surface: the person being counseled uses the same app to keep their own food diary, released plans, training records, and daily check-ins.
- **One account, two surfaces:** any auth user can be the client of another user. The active surface lives in the `prodi_mode` cookie (`lib/client-mode.ts`), switched through `setAppModeAction` (`app/(client)/actions.ts`) from the counselor `UserNav` or the client header. `lib/supabase/middleware.ts` redirects counselor routes to `/klient` while the cookie says `client` — a UX guard only; authorization is RLS.
- **Shell:** `app/(client)/layout.tsx` + `components/client/client-shell.tsx` — mobile-first, bottom nav (Tagebuch, Betreuung), deliberately not the counselor sidebar.
- **Linking:** `client_links` binds a counselor-owned `patients` row to a client account. The counselor creates an invite in the patient tab **Klienten-App** (`components/patient-tabs/klienten-app-tab.tsx` → `createClientInviteAction`); the client redeems it at `/klient/einladung/[code]` or by typing the code under `/klient/betreuung`. Either side can revoke. Self-linking is allowed so one account can test both surfaces.
- **Write model:** `client_links` is read-only through RLS; every mutation runs in a server action with the service-role client, which validates the caller. An unredeemed invite is not readable by its recipient, so redemption cannot go through RLS.
- **Food diary:** `/klient` shows one day (`?datum=YYYY-MM-DD`, defaults to today in `Europe/Berlin`), the five standard meal slots, and kcal/EW/F/KH totals. Entries live in `client_food_log_days` / `client_food_log_entries`, owned by the client. Food search uses the existing `search_foods` RPC; nutrients hydrate through `/api/foods/by-ids`. Data access: `lib/data/client-food-log-client.ts`, math in `lib/client-food-log.ts`.
  - **Four visible sections:** the day is divided into **Wohlbefinden**, **Ernährung**, **Aktivität** and **Sonstiges**, each with its own heading, orientation line and separator. The check-in remains above nutrition so the day's numbers cannot bias it; water, weight and the day note remain after the meals. `components/client/client-food-log-view.tsx` owns the order and section chrome.
  - **Activity is recorded on the day:** `components/client/client-diary-activity.tsx` reads and writes the same `client_workout_sessions` rows as `/klient/training`. A walk or training session can therefore be added, edited and removed without leaving the diary, while the activity tab stays the weekly overview and detailed training workspace. Past diary dates prefill that date in the shared `ClientWorkoutSessionDialog`; the read is guarded by `isClientModuleEnabled("training")`.
  - **Plan and diary are one day.** They used to be strangers: ticking a planned meal wrote a `client_meal_completions` row and nothing else, so a client who followed their plan perfectly had an empty diary, 0 kcal in their Verlauf, and no nutrition data for their counselor — while someone who ignored the plan and typed everything in got complete numbers. The diary now draws the day's planned meals into their slots and counts the ones ticked off. It is a **read-side join, not a copy**: the completion stays the single record of the fact, so the two cannot drift and `client_food_log_entries` keeps meaning "things the client typed in". `client_meal_completions.amount` (migration `20260811000078`, nullable — NULL is "as planned") carries "I ate it, but one and a half portions". The same migration adds `recipe_ingredients_read_linked_client_plan`: migration 73 let the client read a planned recipe's *name*, which meant a recipe entry could be displayed but never costed. `lib/data/client-plan-nutrition-client.ts` normalises both entry kinds to nutrients **per one unit** — one gram of a food, one portion of a recipe — so the same number serves the planned amount and whatever was actually eaten. An entry that cannot be priced contributes nothing rather than a silent zero. The statistics aggregator does the identical sum, otherwise the headline defect would survive in the Verlauf.
  - **Registry exceptions.** The diary has two one-way, guarded reads: `tagebuch → plan` and `tagebuch → training`. Every read sits behind the source module's `isClientModuleEnabled(...)` switch. Turning off the plan removes planned meal rows; turning off training removes the activity section; the rest of the diary keeps working in both cases.
  - **The day has a reference** (`lib/client-targets.ts`, `components/client/client-day-totals.tsx`). Four numbers with nothing to compare them to are decoration. Three sources in descending specificity: the **plan's own total for that date** (macros straight from the plan, not from a percentage split), then `patients.daily_calorie_goal` split by `patients.macro_preset`, then maintenance as basal rate × PAL. A fourth outcome — no reference at all — is respectable and deliberate: a client without a counselor is not handed a target the app invented. Those inputs reach the client through the same fixed projection as the measurement history (migration `20260811000079` adds an `energy` key to `client_patient_history()`); the basal rate is computed **in SQL** by Mifflin-St Jeor so date of birth and sex stay behind it — and since `20260818000091` it resolves as `COALESCE(patients.basal_metabolic_rate_override, formula)`, so a client whose counselor works from a calorimetry reading is not shown a different target than the one they were given. The bars have **no "over budget" state** — a diary that turns red when someone eats is a diary that gets deleted, and judging an overshoot is the counselor's call.
  - **Logging speed**, all derived from the log with no schema: household measures from `food_portions` as one-tap chips (the curated ETL has filled that table since the beginning and only the counselor side read it), with a typical portion as the default instead of a flat 100 g; a "Zuletzt oft" row of this slot's most frequent entries shown *before* anything is typed; and amounts editable in place rather than delete-and-retype. ("Wie gestern" on an empty slot was removed again in August 2026: it took a line of its own in every empty slot to offer what the saved meals below do by name.)
  - **The day's context** (migration `20260811000080`): `client_food_log_days.notes` had existed since the module was built and never had a field — "Einladung bei Freunden", "kaum geschlafen" is the line a dietitian reads first and the one that explains the macros around it. Water gets its own `water_ml` column rather than a nutrient-less catalog entry that every total would have to filter back out; it is counted in glasses because that is how people drink it. Both sit below the meals: a note is written when the day is over.
  - **One search, not four tabs** (`lib/client-food-search.ts`, `components/client/client-food-search-list.tsx`). Filing foods, recipes and saved meals into separate tabs is a filing-cabinet model: it asks the person to know in advance which drawer "Linsensuppe" lives in — catalog food, their counselor's planned recipe, or the meal they saved last week. They do not, so they would search three times. One query spans all three; a badge says what a hit *is* after it is found; filter chips (Alle / Lebensmittel / Rezepte / Meine) narrow afterwards, and only appear when more than one category is present. "Meine" cuts across kinds rather than being one of them. Barcode stays its own mode — scanning is not searching.
  - **Hits identify themselves.** Manufacturer and kcal per 100 g sit in the result list, which is what actually tells six identically named protein bars apart; a click was never the fix, because six clicks are worse than the confusion. Picking one then shows full macros *for the amount being logged*, not for an abstract 100 g. `search_foods` is now called with `requesting_user_id`, which the client surface had omitted — without it a client's own products never appeared in their own search.
  - **Custom products are real foods** (migration `20260811000081`). A scan or a hand-entered product used to be an inline copy on the log row: the same bar scanned twice made two unrelated products, a correction fixed one of them, and "my products" was not a list anyone could show. They are now ordinary `foods` rows with `is_custom = TRUE` and the client as `user_id` — no new table, since RLS already scopes those to their owner and `search_foods` already finds them. `source_food_id` carries the owner (`client:<uid>:ean:<code>`) because `foods` is unique on `(data_source_id, source_food_id)` and two people scanning the same product must not overwrite each other. Three read policies let the linked, consented counselor see them, or a scanned product would render as a blank line on their side — a regression against the inline copy it replaces. `hydrateClientFoods` merges the by-ids endpoint (which strips custom rows on purpose) with an RLS read of the owned ones.
  - **Recipes are logged as recipes** (migration `20260811000083`): `source_type` gains `'recipe'` and the row points at it, with `amount` meaning portions — the same convention `meal_entries` has always used. Exploding a recipe into eight ingredient lines would produce rows the person never entered and cannot correct as a unit; storing per-portion values as a custom entry would display "100 g" for one portion, which is false.
  - **Saved meals** (migration `20260811000082`) are deliberately *not* recipes. A recipe here is a counselor artefact — catalog ingredients, servings, instructions, nutrient targets — and assembling one is a chore almost no client does twice. What people mean by "save this" is far smaller: these four things, under a name, again tomorrow. It is what "wie gestern" was trying to be, under a name the person chose. Logging one writes its items rather than one opaque line, because a bundle the person assembled out of four must stay correctable piece by piece. Private to the client; nothing in it is a record about them that the counselor cannot already see in the diary.
- **Tages-Check-in (`client_daily_checkins`, migration `20260818000093`):** how the day went, asked in the diary itself. Energie, Stimmung and Verdauung (1–5 each, on by default), sleep duration and quality for the night *onto* that date, and alcohol in Standardgläser — a quantity with no energy, since the kcal of a beer come from the diary entry for it. The card sits **above** the day's totals on purpose: someone who reads their kcal balance first rates the balance instead of the day. Saves are debounced with no save button, any past date can be filled in without limit, and an unanswered field stays NULL rather than becoming a low value. A single overall score (1–10) sat above the three until August 2026 and was dropped (migration `20260818000096`): asked first, it was the one that got answered, and the three that would have explained it stayed empty. Registry in `lib/client-metrics.ts`, day assembly and comparison math in `lib/client-checkin.ts`, data access in `lib/data/client-checkin-client.ts`, UI in `components/client/client-checkin-card.tsx`. Registered as the client capability `befinden`.
- **Per-metric switches (`client_metric_preferences`, migration `20260818000094`):** in `/klient/einstellungen`, two switches per metric — anzeigen (is the field asked for in the check-in and drawn in the Verlauf) and teilen (may the counselor see it). Anzeigen was two switches at first, tracken and anzeigen; they were merged in August 2026 because recording something you never look at and looking at something you never record are both combinations nobody wants, and the split only made the screen harder to read. The table keeps both columns and the settings write them together, so rows written under the split keep their meaning; the app reads a row as visible only when both are true. Teilen is inert until an active link carries `consent_wellbeing`. Switching a field off hides it and keeps every value already given. Rows exist only for deviations from the registry defaults.

- **Befinden im Verlauf:** `/klient/statistik` gains a Befinden section with a 14/28/56-day window selector. Every tracked check-in metric with data gets its own line chart — gaps stay gaps (`connectNulls={false}`), unanswered stretches are shaded grey rather than drawn as low values, and days carrying a diary note are marked with a dashed line so an outlier stays explainable. `fetchClientStats` now reads the longer window once and slices the existing fortnight-long charts out of the same rows (`dayFacts`, `notesByDate`).
- **Zusammenhänge:** two user-picked metrics on one dual-axis chart plus a bucket comparison ("an Tagen mit 7–8 h Schlaf: ⌀ …"), with a −3…+3 day shift control that states what it compares as a sentence. Hard rules, all enforced in `lib/client-checkin.ts`: a comparison needs 14 paired days before it says anything, a bucket under 3 days keeps its row and loses its number, quartile buckets are labelled with their real range. The surface never scans pairs, never ranks them, never marks a best shift, and uses no significance language — it is an evaluation tool, and the reading happens with the counselor. Component: `components/client/client-correlation-view.tsx`.
- **Sharing the check-in:** the counselor reads through `client_wellbeing_series(patient_id, from, to)` (migration `20260818000095`), never the table. It checks the active link and `consent_wellbeing`, then emits long format `(date, metric_key, value)` for the metrics the client left shared — an unshared metric produces no rows at all. Consent is granted at redemption, shown as its own bullet on the invite screen, and revocable on its own with a switch in `/klient/betreuung`. The **Klienten-App** patient tab shows the shared metrics with their averages.

- **Counselor view:** the **Klienten-App** patient tab shows link state plus the client's last 7 logged days with kcal per day — read-only, gated on an active consented link. `fetchClientAdherence` returns `{ byDay, bySlot }` from one pass: by day answers "did they follow it", by meal answers "which meal is the problem", and only the second is something to act on — a client can sit at 80 % overall and still skip every dinner.
- **Module registry:** `lib/client-modules.ts` lists the client surface as modules (`tagebuch`, `plan`, `training`, `betreuung`) plus capabilities (`barcode`), which extend a module instead of owning a route. The bottom nav renders from it and each route guards itself with `isClientModuleEnabled`, so flipping `enabled` hides a module including its URL. Every module owns exactly five paths — route, components, `lib/data/client-<id>-client.ts`, migration, spec — and modules normally do not import from each other, which makes removal mechanical. The guarded read-side exceptions are deliberate: the diary draws in the day's released plan and activity sessions because all three describe the same day; switching either source module off removes its section.
- **Plan module (`/klient/plan`):** the client sees the currently released plan for a date and answers each meal with eaten or skipped; tapping the active answer again clears it. Answers live in `client_meal_completions`, keyed uniquely per (client, meal entry), so they remain attached to the exact released revision. Only `active`/`approved` plans are exposed — drafts and replaced/archived stands remain private. A change draft therefore cannot alter the client's current plan, and its release atomically replaces client visibility. Adherence per day appears in the counselor's **Klienten-App** tab.
- **Activity hub (`/klient/training`):** the client landing surface for movement and training rather than another primary entry form. A selected week leads with **active days**, session count, minutes and a Monday-to-Sunday rhythm; the following six-week rhythm separates active days from multiple sessions on the same day. Strength progress is reduced to the three most recently trained exercises, with positive percentage changes and the complete exercise history behind a tap. The selected week's activities render as one compact, progressively disclosed list (three initially); edit, delete, energy estimate and set logging stay inside the opened row. The small header action remains available for backfilling, while an empty week promotes “Erste Aktivität eintragen”. The page loads up to 80 recent sessions so a daily mover does not get falsely empty six-week bars. Sessions still use free-text exercises and sets (reps and/or weight). Progression and rhythm are derived, never stored — `lib/client-training.ts` computes both from the sessions. Deliberately without an exercise catalog; the name is plain text and grouping is case-insensitive, so a catalog stays an additive migration later. Counselor access runs through `consent_training`, separate from the nutrition flag.
  - **Progress measures.** Three per exercise and calendar week, because they answer different questions: heaviest set, estimated 1RM (Epley, `w × (1 + reps/30)`), and volume (Σ reps × kg). The old "heaviest set" rule alone reported no progress for more reps at the same weight and no progress for a fourth set — 1RM catches the first, volume the second. 1RM is the default axis; bodyweight work has none and falls back to reps rather than being drawn as zero. Personal records rank by 1RM and keep the *earlier* set on a tie, so repeating a record does not move the badge to today.
  - **Logging speed** is the thing that decides whether the module is used at all. The set dialog prefills reps and weight from the previous set of that exercise (this session first, then the last session that contained it) and offers **Speichern & weiter**, so three identical sets are three taps; set numbering runs off a mount snapshot plus a local counter so it does not depend on the parent's refresh landing. Each exercise group carries its own **+ Satz**. A session whose title matches an earlier one shows that session's exercises as one-tap chips — nothing is stored for this, it is read back out of the log, so it works retroactively and costs no schema. `components/client/client-rest-timer.tsx` counts up from the last saved set (derived from a timestamp, so a backgrounded tab stays correct).
  - **Energy estimate** (migration `20260810000077`): `duration_minutes`, `activity_kind`, `intensity`, `body_weight_kg` on the session — all nullable, all inputs. The kcal figure is **not** stored; it is derived like progression, so correcting the duration corrects the number. `body_weight_kg` is captured at logging time on purpose: expenditure scales with body weight, and reading the nearest measurement instead would make the module depend on a table it does not own and silently rewrite old sessions whenever someone steps on a scale. MET values (Compendium of Physical Activities, three effort levels per activity) live in **`lib/energy-expenditure.ts`**, shared with the counselor surface — note this when deleting the module. `activity_kind` is a plain key with an app-side lookup and a neutral fallback, same reasoning as the free-text exercise names.
  - **Two decisions about not overstating it.** The headline figure is **net** — `(MET − 1)` — not gross: gross includes the resting metabolism of the same hour, roughly 80 kcal for an 80 kg person, and in a nutrition app that difference is what gets eaten back. Every result carries a range (±30 % for resistance work, whose true cost depends on rest intervals nobody logs). The estimate is shown beside the food in the Verlauf, never stacked with it and never subtracted from it.
  - The same table replaced the counselor's flat `weight × 5` activity estimate in `components/patient-tabs.tsx` and the flat `durationMinutes × 4.5` fallback in `components/patient-stats-tab.tsx`; free-text activity names are matched by keyword (`matchActivityByName`).
- **Barcode lookup (capability, not a module):** the add-entry dialog has a **Barcode** tab next to the search. `GET /api/foods/barcode/[code]` (`app/api/foods/barcode/[code]/route.ts`) resolves a code in three tiers — the local catalog (OFF imports keep the barcode in `foods.source_food_id`, so the existing unique index answers it and no mapping table exists), then the Open Food Facts API by code, then a short manual form. Tiers 2 and 3 both produce a `custom` entry with per-100 g nutrients; scans never write to `foods`. GTIN rules incl. the check digit live in `lib/barcode.ts`, OFF parsing in `lib/off-product.ts` (shared with `scripts/etl/import-off.ts`). Switched via `isClientCapabilityEnabled("barcode")` — a capability extends a module instead of owning a route, since scanning fills the diary rather than being a place to navigate to.
- **Verlauf — measurement history:** the client sees the same weight / BMI / body-composition charts the counselor has, over the whole record, by reusing `PatientStatsTab` itself rather than a copy. Access runs through the `client_patient_history()` RPC (migration `20260810000075`), **not** a SELECT policy: RLS grants rows, and `patients` and `patient_anthropometrics` both carry counselor `notes` (plus insurance and address columns) that the client must never receive. The function returns a fixed projection, so the column list *is* the permission and sits in one reviewable place. `tests/client-history-rls.spec.ts` asserts the omissions as hard requirements — notes and insurance number absent from the payload, the underlying tables still closed to a direct read, nothing at all for an unlinked account or after revocation. `PatientStatsTabProps.patient` is narrowed to `Pick<Patient, "firstName" | "goalWeight">` (all the charts read), so no fuller patient object has to cross into the client app; counselor sessions are passed empty and the "N Beratungen" line hides itself rather than claiming zero.
- **Verlauf module (`/klient/statistik`):** split into an **Ernährung** and a **Training** section, because the page answers two different questions and a wall of undifferentiated cards makes the reader do the sorting. Nutrition: kcal per day over 14 days with an average line and, beside it, the estimated energy spent training; plan adherence as a stacked bar (gegessen / ausgelassen / offen); and estimated 1RM per exercise and calendar week. Eaten and burned sit side by side, never stacked and never subtracted: two different measurements, only one of them counted rather than estimated. Training alone is enough to draw the chart. Exercises with no 1RM to plot (bodyweight) are filtered out of the chart and its legend but keep their line in the text list below it. The 1RM axis uses a padded domain rather than a zero baseline — an eight-kilo gain plotted from zero is a flat line, and a line carries no area to oblige one. Training additionally shows sessions and volume **per week** (`summarizeTrainingWeeks`) plus personal records: a day is the wrong grain, since nobody trains daily and a daily series is mostly zeros that read as failure where the truth is "three times a week, as planned". The only client module that reads the others instead of owning data: it has **no migration** because it stores nothing, and every section is guarded by `isClientModuleEnabled`, so the dependency runs one way and switching a module off removes a section rather than breaking the page. Arithmetic lives in `lib/client-stats.ts` (pure, tested): untracked days are filled with zero so a diary with holes looks like one, and the average counts only logged days — dividing by the whole window would punish the gap rather than describe the food. Series colors are the app's chart tokens in fixed order, green/blue/red; the violet step is deliberately skipped because it sits within ΔE 7.2 of the blue one under deutan vision.
- **Camera scanning (`components/client/client-barcode-scanner.tsx`):** native `BarcodeDetector` where it exists, `zxing-wasm` everywhere else — which on iPhone is the normal case, since Safari has none. The component is `dynamic(..., { ssr: false })` so the ~1 MB decoder only loads when someone opens the camera, and the wasm is served from `/zxing/` (copied out of `node_modules` by `scripts/copy-zxing-wasm.mjs` via `predev`/`prebuild`, gitignored) instead of the CDN zxing-wasm would otherwise fetch per scan. Frames are downscaled to 640 px and decoded at ~7 fps against EAN-13/EAN-8/UPC-A/UPC-E; tracks are stopped on unmount, not just on the close button, so the camera indicator cannot stay lit. The typed-code field remains permanently — denied permission must not be a dead end.
## 5. Supporting Modules
- **Navigation performance (app-wide):** every route under `app/(app)` is dynamic, because the shell resolves the session. Three things keep that cheap:
  - **Local session verification (`lib/supabase/verified-user.ts`):** `getVerifiedUser()` verifies the session JWT against the project's public signing keys (JWKS cached in `lib/supabase/jwks.ts`) instead of calling `supabase.auth.getUser()`, which is a network round trip to the Auth server — measured at 60-300ms, and previously paid two or three times per navigation by the layout, the page and their helpers. Wrapped in React `cache`, as are `createClient()` and `fetchCurrentMembership()`, so one request performs one verification and one membership lookup. Tradeoff (the same one already approved for the middleware): a revoked user keeps access until their token expires. Data access is unaffected — RLS validates the token on every query.
  - **`loading.tsx` on every route (`components/page-skeletons.tsx`):** a click paints immediately instead of freezing the previous screen. It also does load-bearing work for prefetching: Next.js only prefetches a dynamic route as far as its nearest `loading.tsx`, so without one, hovering a link warms nothing.
  - **Prefetching left on:** `prefetch={false}` disables prefetch on hover *and* viewport in the App Router, so it is not used. It was removed from 21 call sites, including the sidebar.
- **Error boundaries:** `app/(app)/error.tsx` keeps the shell and its navigation alive when a route fails, and shows the `digest` rather than the raw Postgres message. `app/global-error.tsx` is the last resort for a root-layout failure and ships its own inline-styled markup, since no provider is available there.
- **Client-side data discipline:** three faults here cost more than anything on the server, and the pattern is worth not repeating.
  - **Unstable array in a dependency list.** `useRecipes(recipes, [])` passed a fresh `[]` on every render into an effect's dependency list. The effect fetched, set state, re-rendered, and re-armed itself — 132 requests in 12 seconds, saturating the connection pool and slowing navigation across the whole app. The hook now holds `foods` in a ref so it cannot be re-armed this way, and the call site hoists the array to a module constant.
  - **Global reference data pulled per component, per page.** All ~7,000 system food synonyms (1.8MB, 8 sequential round trips) were downloaded by each consumer of `useFoodSynonyms`, one of which is the command palette in the app shell — so it happened on every navigation. Now: one module-level cache and one shared in-flight promise, the search surfaces pass `enabled` so the download waits until they open, and `fetchSystemFoodSynonyms` requests the remaining pages in parallel off an exact count.
  - **Deriving state from data fetched only in the browser.** Aufnahmen derives its stages from invitations and questionnaires, which arrived two round trips after the page. They are now fetched in `page.tsx`. Intake *links* need `lib/data/patient-intake-server.ts` rather than the client reader, because a link's public URL comes from `window.location.origin` — empty on the server.
  - **Prefetching on repeating rows.** `prefetch={false}` stays on list rows: with 52 patients, every visible row otherwise prefetches its own detail page. The sidebar, breadcrumb and header buttons keep prefetching, because those are the navigation.
- **Header breadcrumb (`components/app-breadcrumb.tsx`):** The app shell header carries the trail beside the search, so every route says where it sits in the same place. `deriveBreadcrumb()` walks the path segments against `NAV_SECTIONS` (so the trail and the sidebar can never disagree on a label) plus a small dictionary for segments the sidebar does not name (`neu`, `bearbeiten`, `beratungen`, …); opaque uuid and numeric segments are dropped rather than printed. A page whose name lives behind an id supplies the finished trail through `useAppBreadcrumb()` — the patient record does this in `patient-detail-client.tsx`, turning `/patienten/<uuid>` into `Patienten › Daniel Spallek`. Ancestors are hidden below `sm`. This is separate from `components/page-breadcrumb.tsx`, which is the in-page header row of a full-bleed list page and also carries that page's `h1` and action buttons.
- **Food Search Command (`components/food-search-command.tsx`):** Global command palette. Lazy-loads the search index from `/api/foods/search-index` (authenticated, catalog-only) on first use; the user's own custom foods are merged in `FoodSearchProvider` via the RLS-scoped client fetch.
- **Nutrient utilities (`@/lib/nutrients.ts`):** Mathematically validated core logic. Handles ingredient scaling and summing.
- **Fuzzy Search (`@/lib/search/fuzzy-search.ts`):** Optimized client-side search over the food index using Trigram similarity and Cologne phonetics.
- **Exports (`lib/exports/*`):**
  - `constants.ts` defines allowed format/scope combinations.
  - `pdf.tsx` contains branded PDF rendering for reports and patient documents.
  - `report-builder.ts` creates meal-plan report payloads for clinical reports, patient handouts, and Lehrküchen exports.
  - `server.ts` centralizes file responses and export job creation.

## 6. Scripts & ETL

- **BLS Import (`scripts/etl/import-bls.ts`):** Syncs the 7,140 food items from the Excel source to Supabase.
- **SFK Import (`scripts/etl/import-sfk.ts`):** Imports Souci-Fachmann-Kraut foods and nutrients (requires paid license and `SFK_SOURCE_FILE` env var). Uses `scripts/etl/sfk-shared.ts` for column mapping. Verify with `npm run etl:verify:sfk`. Requires the `20260513000030_sfk_nutrient_definitions.sql` migration for the expanded nutrient groups (`aminosaeuren`, `fettsaeuren`).
- **OFF Integration (`scripts/etl/import-off.ts`):** Implements the "Quarantine Pipeline" for branded products from Open Food Facts. Defaults to German products, paginates up to 500 products, supports JSON/JSONL source files or URLs, stages raw rows plus provenance metadata in `off_staging`, validates nutrition plausibility, computes a `data_quality_score`, and promotes only validated rows above the configured quality threshold to `foods` + `food_nutrients`.
- **OFF Pre-filter (`scripts/etl/filter-off.ts`):** Creates a smaller import file from the very large Open Food Facts JSONL export by keeping only products with the configured country tag and mapped energy/nutrition keys. Use before `etl:off` for local full-export imports.
- **German Synonyms (`scripts/etl/generate-synonyms.ts`):** Generates regional and colloquial German food name synonyms (Karotte/Möhre, Quark/Topfen, etc.) for improved search. Run with `npm run etl:synonyms`.
- **Portion Sizes (`scripts/etl/import-portions.ts`):** Imports curated German portion sizes from `lib/reference-data/food-portions.ts`, matching BLS foods by code prefix or food group. Run with `npm run etl:portions`.
- **Reference Values (`scripts/etl/import-reference-values.ts`):** Imports DGE reference values.
- **Recipes & Meal Plans (`scripts/etl/import-recipes-and-meal-plans.ts`):** Imports shared recipes and meal plan templates.
- **Master Orchestrator (`scripts/etl/run-all.ts`):** Runs the full ETL pipeline in order (BLS → verify → synonyms → portions → reference values → recipes → OFF). Supports `--dry-run`, `--skip`, and `--only` flags. Run with `npm run etl:all`.
- **Clinic Demo Seed (`scripts/seed-clinic-demo.ts`):** Refreshes the full buyer-story demo workspace for a selected Supabase Auth user. Run with `DEMO_USER_EMAIL=<account-email> SUPABASE_SERVICE_ROLE_KEY=<service-role-key> npm run seed:clinic-demo`; add `-- --dry-run` for credential and food availability checks without writes.
- **Scientific Validation (`scripts/validate-nutrient-math.ts`):** Running `npm run validate:nutrients` performs 113+ mathematical assertions to ensure calculation parity with official standards.

- Search: open global search with `Cmd+K`; first open should load the index, later opens should be instant.
- Foods browser: on `/lebensmittel`, verify page navigation, source/category filters, and typo-tolerant search still work.
